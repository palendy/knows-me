## 0. 인텐트 분석 요약 (Intent Analysis)
- **사용자 요청**: "knows-me 서비스를 구축하고 싶다. 요구사항 파일을 읽고 AI-DLC 워크플로우를 시작하자."
- **요청 유형**: New Project (Greenfield)
- **범위 추정**: System-wide (다중 컴포넌트 — 데스크탑 앱, 소스 커넥터, 가공/LLM, 로컬 서버/API, 다수 UI)
- **복잡도 추정**: Complex
- **요구사항 깊이**: Comprehensive
- **프로젝트 성격**: 개인용(1인) PoC 지향. 데이터 모델·구조는 다중 사용자 확장을 대비해 설계.

## 1. 개요

### 1.1 비전
에이전트 세션·외부 시스템·파일 등 흩어진 나의 흔적을 모으고, 인터뷰로 보충·구체화하여
"나"를 정확히 아는 구조화된 개인 맥락 데이터베이스를 만들고, 그 맥락을 여러 인터페이스로 제공한다.

### 1.2 핵심 가치 제안
- **나의 관점**: 기존 에이전트 메모리와 달리, 내가 선호하는 정보를 내가 원하는 형태로 정확히 보유(확인을 거친 것만 축적).
- **활용 관점**: 내가 없어도 나의 맥락을 아는 에이전트/아바타가 팀에서 나의 일처리를 대신.

### 1.3 사용자 / 페르소나 (초안 — User Stories 단계에서 구체화)
- **소유자(Owner, 나)**: 유일한 1차 사용자. 수집 관리, 인터뷰 응답, 조회/대화, 설정.
- **제3자 소비자(향후)**: 소유자의 페르소나 API/아바타를 소비하는 외부 사람/에이전트. **MVP 범위 아님**(로컬 전용).

## 3. 기능 요구사항 (Functional Requirements)

### FR-1 소스 수집 (Ingestion)
- **FR-1.1 에이전트 세션**: Claude Code, Codex 로컬 세션/트랜스크립트를 증분 수집. 트리거는 **주기적 배치(기본)**, 이후 **파일 감시**, **수동 "지금 수집"** 순으로 제공(D5). MVP **1순위** 소스.
- **FR-1.2 외부 시스템**: 공식 API 연동. MVP 1차 대상 **Notion, Gmail**(D6). "내 것"만 필터(내가 작성/수신/담당). 증분 동기화. 자격증명 암호화 보관(FR-5).
- **FR-1.3 파일**: 이미지·텍스트·오피스 파일. **알려진 폴더 감시(기본) + 수동 업로드(보조)**. 이미지는 LLM 비전으로 텍스트 맥락 추출. 텍스트/오피스는 본문 파싱.
- **FR-1.4 (향후) 카카오톡**: 수집 방식 미정 — 범위 외.

### FR-2 데이터 가공 (Processing)
- **FR-2.1**: 원본을 그대로 저장하지 않는다. 반복되는/필요한 것만 요약·분류. 일회성·잡음 제거.
- **FR-2.2**: 불확실하거나 더 알아야 할 것은 인터뷰 Queue(FR-4)로 이관.
- **FR-2.3 클라우드 전송 마스킹(D2)**: LLM 호출 전 식별정보(이름·이메일·전화·계정·토큰 등)와 비밀을 최대한 제거/치환한 뒤 요약·분류·추론을 요청. 원문은 로컬에만 보관.

### FR-3 Knowledge DB
- **FR-3.1 저장 형태(D3)**: 사실(fact) 하나 = 하나의 문서(마크다운/JSON). 문서 간 링크로 "LLM 위키" 구성. 검색/조회용 인덱스 유지. 그래프 뷰는 문서 간 링크에서 도출.
- **FR-3.2 메타데이터(각 사실)**: 출처(소스·수집시각), 확인 여부, 회사/개인 구분, 확인일.
- **FR-3.3 변경 이력**: 같은 사실 갱신 시 덮어쓰지 않고 이력 보존(추적 가능).
- **FR-3.4 다중 사용자 대비(D9)**: 스키마에 소유자 식별/접근범위 필드를 두어 향후 확장 가능하게(구현은 1인용).

### FR-4 인터뷰 Queue
- **FR-4.1 아이템 생성**: 수집·가공 중 자동 생성. 종류 2가지 — **사실 후보(확인형)**, **질문(심화형, 답의 단어로 다음 질문 연쇄)**.
- **FR-4.2 우선순위/만료**: 아이템 우선순위 부여, 오래되거나 반복되는 항목은 정리(만료/억제).
- **FR-4.3 답변 UX**: 사용자가 **원할 때** 답변(강제 없음). 각 아이템에 **답변 선택지 + 직접 입력** 제공. **Queue 화면 안에서 화면 전환 없이** 처리. 확인/답변된 것만 Knowledge DB 반영. 답변은 새 질문 생성 근거가 됨.

### FR-5 보안 (기능 측면)
- **FR-5.1 로컬 전용 저장**(클라우드 저장 없음).
- **FR-5.2 저장 암호화**: 맥락 데이터 및 외부 시스템 자격증명 암호화.
- **FR-5.3 키 관리**: 최초 설치 시 비밀번호 설정 → 키 유도 함수(Argon2/PBKDF2)로 키 생성 → 대칭키 암호화(AES-256-GCM). 앱 실행/잠금 해제 시 비밀번호로 키 재유도, 평문 데이터 키는 디스크에 저장하지 않음.
- **FR-5.4 자격증명 보관**: 외부 시스템 토큰/OAuth 자격증명 암호화 저장.

### FR-6 인터페이스 (데스크탑 앱)
- **FR-6.1 대시보드**: 수집 현황, 대기 Queue 개수, 최근 확정 사실 등 상태 표시.
- **FR-6.2 미니홈피("싸이월드") 뷰**: 확정된 나의 맥락을 미니홈피 스타일로 한 화면에 시각화.
- **FR-6.3 지식 그래프 뷰**: Knowledge DB(문서 링크)를 노드/관계 그래프로 탐색.
- **FR-6.4 페르소나 챗 UI**: 나의 맥락 기반 페르소나 아바타와 대화. 소비자: 나(또는 향후 타인). **MVP는 로컬**.

### FR-7 페르소나 활용 API
- **FR-7.1 로컬 서버(D8)**: 앱 내장 로컬 서버가 REST API/챗을 제공. 앱 실행 중에만, 로컬에서 접근. **MVP는 외부 노출·인증 없음(D7)**.
- **FR-7.2 기능(최우선)**: "나 대신 네트워킹"(메일/메신저/게시글 초안 작성 등). (심화) "나 대신 회의 참석"(회의 이해, 페르소나 응대) — 심화는 후순위.
- **FR-7.3 (향후) 접근 제어**: 원격 노출 시 API 키/스코프 권한 도입.

## 4. 비기능 요구사항 (Non-Functional Requirements)
- **NFR-1 플랫폼(D4)**: Windows/macOS/Linux 데스크탑. 구현 부담 과도 시 우선순위 축소 허용.
- **NFR-2 프라이버시**: 저장은 로컬·암호화. 클라우드 LLM 전송분은 마스킹·최소화(D2). 어떤 데이터가 외부로 나가는지 사용자가 인지 가능해야 함(투명성).
- **NFR-3 로컬 우선/오프라인**: 수집·저장·조회는 로컬에서 동작. LLM 의존 기능(요약/비전/대화)은 네트워크 필요 — 미연결 시 우아하게 저하(수집·조회는 계속 가능).
- **NFR-4 규모**: 개인 데이터 규모(1인) 가정. 수천~수만 사실 문서에서 조회·검색이 반응성 있게 동작.
- **NFR-5 증분/멱등 수집**: 재수집 시 중복 없이 신규분만 반영(멱등).
- **NFR-6 이식성**: 저장 포맷은 사람이 읽을 수 있는 파일 기반(마크다운/JSON)으로 이식·백업·수동 편집 용이.
- **NFR-7 확장성(모듈)**: 소스 커넥터는 플러그형 구조(세션→Notion/Gmail→기타 순차 추가).
- **NFR-8 테스트(PBT Partial)**: 속성 기반 테스트 부분 적용 — PBT-02(왕복), PBT-03(불변식), PBT-07(생성기 품질), PBT-08(축소/재현), PBT-09(프레임워크 선정) 강제. 특히 **직렬화/역직렬화(사실 문서 ↔ 모델)**, **암호화/복호화 왕복(FR-5)**, **마스킹 함수 불변식**에 적용.

## 5. 범위 (Scope)

### 5.1 MVP 포함
- 소스 수집(세션 1순위 → Notion·Gmail → 파일; 이미지 비전 포함)
- 가공(마스킹 포함) 및 Knowledge DB(메타데이터·변경 이력, 파일 기반 위키)
- 인터뷰 Queue(확인형+심화형, 선택지+직접입력, 전환 없는 UX, 우선순위/만료)
- 인터페이스(대시보드, 미니홈피 뷰, 지식 그래프, 페르소나 챗 UI)
- 페르소나 로컬 API("나 대신 네트워킹" 우선)
- 보안(로컬·암호화·설치 시 비밀번호)

### 5.2 범위 외 / 향후
- 카카오톡 수집(FR-1.4)
- 권한 기반 다중 사용자 및 원격 API 노출/인증(D7, D9)
- "나 대신 회의 참석" 심화(FR-7.2 심화분)
- 팀 맥락 집계

## 6. 가정 및 리스크 (Assumptions & Risks)
- **A1**: LLM은 이미지 비전 입력을 지원한다(원본 가정 유지).
- **A2(수용된 트레이드오프)**: 클라우드 LLM 사용으로, 저장은 로컬이어도 가공 시 (마스킹된) 데이터가 외부 API로 전송된다. 개인 PoC로서 수용(보안 익스텐션 미적용).
- **R1**: 마스킹이 완전하지 않으면 민감정보가 유출될 수 있음 → 마스킹 규칙 검증(PBT)·전송 투명성(NFR-2)으로 완화.
- **R2**: 에이전트 세션 파일 경로/포맷(Claude Code/Codex)은 구현 시 확정 필요.
- **R3**: Notion/Gmail API 인증 스코프·"내 것" 필터 기준은 커넥터 설계 시 확정.
- **R4**: 파일 기반 위키의 그래프/검색 성능은 규모 증가 시 인덱싱 전략으로 관리.

## 7. 성공 기준
- 아무 프로젝트 폴더에서 새 세션을 열고 "이거 어떻게 띄워? 규칙은?"을 물으면 설명 없이 답한다.
- 세션/Notion/Gmail/파일에서 수집→가공→Queue 확인→Knowledge DB 반영이 한 흐름으로 동작한다.
- 페르소나 로컬 API로 "나 대신" 초안 작성이 가능하다.

## 8. 핵심 요구사항 요약
knows-me는 **로컬 우선 Tauri 데스크탑 앱**으로, 에이전트 세션·Notion·Gmail·파일에서 나의 흔적을 수집하고,
**마스킹 후 클라우드 LLM**으로 요약·분류하여 **파일 기반 "LLM 위키"** 형태의 Knowledge DB에 확인된 사실만 저장한다.
불확실한 것은 **인터뷰 Queue**로 사용자에게 되묻고, 확정된 맥락을 **대시보드·미니홈피·그래프·페르소나 챗/로컬 API**로 제공한다.
저장은 비밀번호 기반 대칭키 암호화로 보호하며, 다중 사용자·원격 노출은 향후 확장으로 설계만 대비한다.
