# knows-me — 컨셉 변경 공유 (팀원용)

> 2026-09-09 · 대상: 팀원 · 상태: 컨셉 확정, 기능 구현 착수 전 (아래 "사용 예시"는 **목표 UX**)

## 한 줄

**세션 수집 → 내 CLAUDE.md 채우기**에서 →
**내 지식을 공용/개인으로 나눠, 나도 쓰고 팀원의 에이전트가 MCP로 질의하는 개인 지식 위키**로 컨셉을 조였습니다.

## 뭐가 바뀌었나

| | 이전 | 이후 |
|---|---|---|
| 소비자 | 나 하나 (내 세션에서 Claude가 읽음) | **나 + 팀원(과 그 에이전트)** |
| 산출물 | Claude가 읽는 CLAUDE.md 파일 | **MCP로 질의되는 지식 위키** |
| 접근제어 | 없음 | **공용/개인 분류 + 범주별 토큰 스코프** |
| 가치 | "내 방식 재설명 안 해도 됨" | "**내가 없어도 내 지식을 팀이 참조**" |

## 팀원 입장에서 뭐가 좋나

내게 일일이 물어보지 않아도, **당신의 에이전트가 내 지식에 직접 질의**합니다. 내가 부여한 범주 안에서만요. (그 밖은 존재조차 안 보입니다.)

### 사용 예시 (목표 UX)

**1. 내 MCP를 당신 Claude Code에 등록** — 내가 준 URL + 토큰 한 줄:

```bash
claude mcp add --transport http jibin-knows-me \
  https://<tunnel-or-localhost>/mcp \
  --header "Authorization: Bearer <내가-발급한-토큰>"
```

**2. 그다음부터는 그냥 물어보면 됩니다** — 당신 에이전트가 알아서 내 지식을 참조:

```
너: "지빈이 맡은 결제 서비스 로컬에서 어떻게 띄워?"
에이전트: (jibin-knows-me MCP 질의) → "run.sh로 띄우고,
          .env는 1Password의 payment-dev 항목을 쓴다고 되어 있어요."

너: "이 리포 배포 규칙 있어?"
에이전트: (deploy 범주 조회) → "main 직접 푸시 금지, PR + 코드리뷰 xhigh 통과 후 머지."
```

**3. 내가 안 준 범주는 안 보입니다:**

```
너: "지빈 연봉 협상 메모 있어?"
에이전트: → 그런 지식에 접근 권한이 없습니다. (forbidden)
```

## 나(오너) 입장 요약

- **나도 소비자다** — 내 localhost MCP로 내 지식 전부를 질의해 작업 효율을 올립니다.
- **공유는 내 승인으로만** — 자동 수집물은 기본 private. Queue에서 *"공용으로 풀까? 어느 범주로?"*를 내가 확인한 것만 팀에 노출됩니다.
- **토큰은 per-consumer 발급/폐기** — 팀원마다 다른 토큰, 부여 범주도 다르게.

## 보안 · 프라이버시 (핵심 3줄)

1. **기본 private.** 명시 승인 + 범주 부여한 것만 공유. 시크릿은 수집 시점에 레닥션.
2. **데이터는 내 기기 밖으로 안 나감.** 스냅샷을 뿌리는 게 아니라, 라이브 스코프 질의 결과만(범주 + 레닥션) 전달.
3. **인가는 서버가 강제.** 신원·범주는 토큰에서만 나오고, 요청 인자로는 못 넓힘.

## 대략 작업 플로우 (강화 컨셉 구현)

파이프라인은 그대로 두고, 분류/공유 축을 새로 얹습니다.

```
수집 → 가공·시크릿 레닥션 → Queue(확인 + 공용/범주 승인) → 지식 위키(로컬 암호화)
     → MCP 서버(토큰-스코프 인증) → 나(localhost) / 남(터널+토큰, 부여 범주만)
```

**계약 우선**: MCP 툴 계약(`list_categories` / `search_knowledge` / `get_page` / `get_guide` + 스코프·에러 시맨틱)을 먼저 확정하고, 4명이 그 계약에 맞춰 병렬 진행합니다.

## 4명 분담 (동시 진행)

기존 U1~U4 오너십을 유지하고, 강화 컨셉 작업만 각자 영역에 매핑합니다.

| 오너 | 강화 작업 |
|---|---|
| **U1** 코어·보안 | 토큰 발급/폐기 + 스코프 모델(고엔트로피, per-consumer grant), 서버 단일 인가 지점, MCP 트랜스포트(Streamable HTTP) + 인증 미들웨어, 터널 배선 |
| **U2** 수집·가공 | 수집 시점 시크릿 레닥션, 공용/개인 분류 후보 태깅, 위키 구조화 |
| **U3** 지식·인터뷰 | 위키 데이터모델에 공용/개인·범주 필드, Queue를 "공개 승인 + 범주 지정" 게이트로 확장, 심화 인터뷰 |
| **U4** 인터페이스·페르소나 | MCP 툴 표면 + 도메인 로직, 프롬프트 인젝션 안전 서빙, 위키 뷰(사람용), 오너 셀프 참조 UX |

**순서**: U1이 토큰·스코프·서버 뼈대(계약)를 먼저 → U3 데이터모델·게이트 / U2 레닥션·분류 / U4 MCP 툴을 병렬로 → 통합. 전체 우선순위는 **ⓐ 오너 셀프 참조 완성 → ⓑ 팀 공유**.

## 동시 작업 방식 (어떻게)

이 리포가 초안에서 이미 쓴 방식 그대로 갑니다 — **계약 우선(contract-first) 병렬**. 4명이 서로를 기다리지 않게 하는 게 핵심입니다.

1. **계약부터 동결.** 코드 전에, 병렬을 가능케 하는 공유 계약 3개를 먼저 확정합니다. (계약 초안은 한 명이 먼저 잡아 공유 → 나머지가 리뷰)
   - **MCP 툴 계약** — 툴 이름·입출력 스키마, 스코프/권한 시맨틱, 에러(`unauthorized` vs `forbidden`), 가산적 버저닝.
   - **지식 데이터모델** — `visibility`(공용/개인) + `category` + grant 필드.
   - **토큰·스코프 계약** — 토큰 → 부여 범주 집합, 서버 강제, 인자는 좁히기만.

   이걸 타입/목(mock)으로 박아두면 나머지가 실물 없이도 붙습니다.
2. **1인 1유닛, 브랜치별 작업, 목(mock) 상대로 개발.** 각자 자기 유닛 브랜치에서 계약 + 목에만 의존. U1이 이미 목을 제공.
3. **의존 순서.** U1이 토큰·스코프·서버 뼈대(= 계약 enabler) + 목을 먼저 랜딩 → 그다음 U2/U3/U4 병렬 → 통합 → 공용 Build & Test.
4. **세로 슬라이스 먼저.** ⓐ 오너 셀프 참조(localhost, 나 혼자 end-to-end)를 먼저 관통시키고 → ⓑ 터널 + 다중 소비자로 확장.
5. **경계 위생.** 남의 유닛 파일 안 건드림. 공용 파일(`Cargo.toml`/`lib.rs` 등)은 가산적 변경만. PR + 코드리뷰, main에 자주 rebase, 작은 커밋.
